# 0008. 词组复用改用统一引用关系（DAG），不再做父子继承

- 状态：已接受
- 日期：2026-11-05

## 背景

用户希望词组之间能体现复用关系，并能在详情页跳转查看。最初设想是"父词组 / 子词组"的单父继承，随后又提出"像 Java 一样多继承"是否可行。

讨论中发现两个问题：

1. 多父继承会让关系变成有向图，必须引入环检测、深度限制和优先级规则，用户也明确表示"看不懂术语"；
2. 真正的痛点不是继承语义，而是：导入多个词组库后条目堆在自有区、看不出复用了谁、来源改动不同步。

## 决策

放弃 `parent_id` 单父继承，改为**统一引用关系**：

- 新增 `group_ref(group_id, ref_group_id, priority, sort_order)`，同一组内引用唯一；
- 引用是 DAG，写入时做自引用 / 重复 / 成环 / 跨范围校验；
- 条目**不复制**，详情读取时按 BFS 递归展开引用链（深度 ≤ 10），`tagId|polarity` 去重，自身 > 近层 > 远层；
- 被引用的组禁止删除，报错时列出引用方，由用户先解除引用。

## 后果

好处：

- 来源组改动自动同步，不再有"导入即冻结"的问题；
- 详情页按来源分组 + 超链接，复用了谁一目了然；
- 复制拼接走 `effectiveItems`，引用的条目会一起被带出；
- 单一关系模型，不再需要区分"继承"和"导入"两套语义。

约束与成本：

- 每次详情都要递归查询，深度与引用数量会带来额外查询开销；
- 环检测、删除保护、范围校验都必须在服务端兜住，前端不能省；
- `tag_group.parent_id` 成为历史列，旧数据需迁移。

## 备选方案

- **单父继承（parent_id）**：实现最简单，但只能表达一条复用链，不满足"引用多个词组库"。
- **多父继承**：能表达复用，但本质与引用相同，还要额外定义"继承"与"导入"的差异，概念成本高。
- **导入时拷贝条目**：实现直接，但来源改动不同步、条目堆叠不可追溯，正是用户要解决的问题，否决。
