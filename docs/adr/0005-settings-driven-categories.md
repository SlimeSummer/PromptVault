# 0005. 分类与底模改为设置驱动

- 状态：已接受
- 日期：2026-11-03

## 背景

词条分类和 LoRA 底模最初是硬编码的：分类同时写在后端 `TagService` 与前端页面里，底模写在前端页面里。
用户希望能在界面上自行增加、删除、修改分类，以及补充新的底模（例如 anima）。
每次新增选项都要改代码、重新构建，体验不可持续。

## 决策

用已有的 `setting` 表存储配置，不新增表：

- `tag.categories`：JSON 数组，元素为 `{ value, label }`；
  - `value` 是数据存储用的稳定标识（字母/数字/下划线/短横线），创建后不可修改；
  - `label` 是界面显示名称，可随时修改。
- `lora.base_models`：JSON 字符串数组。

规则：

- 删除仍被词条使用的分类时拒绝操作，并提示剩余词条数量；
- 分类顺序即显示顺序，后续表头排序也按这个顺序；
- 后端所有分类校验、统计、下拉选项都从 `SettingService` 读取，不再有第二份枚举。

## 后果

- 不新增表、不迁移数据，老库直接可用（`setting` 表在阶段 0 已建）。
- 分类标识不可改，历史 `tag.category` 永远能对应上；改中文名不影响数据。
- 自定义分类不会进入自动分类规则（批次 D），需要手动选择。
- `SettingService` 成为分类的唯一事实来源；后续词组、编辑区都必须走它，避免再次硬编码。

## 备选方案

- **新建 `category` 表**：更"数据库范式"，但需要给 `tag` 增加外键或改名迁移，收益不足以抵消成本。
- **允许修改分类标识并级联更新 `tag.category`**：灵活，但一次误改会批量改写历史数据，风险高。
- **保持硬编码，只允许改显示名称**：改动小，但无法真正新增分类，不满足需求。
